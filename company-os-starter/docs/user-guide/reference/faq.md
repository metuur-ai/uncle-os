# Frequently asked questions

Short answers with a pointer to the page that goes deeper. If your question
is a symptom ("command X fails with Y"), start at
[reference/troubleshooting.md](troubleshooting.md) instead.

## Concepts

**What is Company OS, in one sentence?**
A Git-based operating system for running governance, product, and engineering
work as validated Markdown + YAML — files, a CLI that guides you through them,
and a validator that keeps everyone honest. No SaaS, no database.

**Is Team OS a different product?**
No. "Team OS" is just Company OS running with only the `teams/<t>/` layer
present — one team, no platform or company layer above it. The team-layer
shape never changes, so you can start standalone and grow into a full
federation later without restructuring. See
[tutorials/02-running-a-standalone-team.md](../tutorials/02-running-a-standalone-team.md).

**Do I need the whole company/platform/team hierarchy to start?**
No. A single team is a valid workspace; the CLI degrades gracefully around
the layers that aren't there. Add a platform or company layer when you
actually need one — [how-to/grow-a-workspace.md](../how-to/grow-a-workspace.md).

**Is there a server or database to run?**
No. Everything is files in Git. Company OS only writes and validates files;
Local Search reads them into a local, disposable index. Any tool that can
read a file can participate — [explanation/how-it-fits-together.md](../explanation/how-it-fits-together.md).

## Governance and rules

**What do the rule tiers mean?**
- **mandatory** — a guaranteed outcome; escapable only via an approved,
  expiring *exception*.
- **default** — comply or explain via a *deviation*.
- **guidance** — advisory, untracked.

Tiers are what let a company enforce outcomes while teams keep flexibility in
*how* they work.

**Deviation vs. exception — which do I file?**
File a **deviation** to opt out of a *default*-tier rule (comply-or-explain,
with a `reviewDate`). File an **exception** to get temporary relief from a
*mandatory* rule (needs approval and an `expires` date). Both must carry a
future date. Walkthrough:
[how-to/handle-a-deviation-or-exception.md](../how-to/handle-a-deviation-or-exception.md).

**Why won't the CLI let me deviate from a mandatory rule?**
By design — mandatory rules are non-negotiable outcomes. The only escape hatch
is a time-boxed exception, so the relief is visible and expires rather than
becoming permanent drift.

**Who owns a component — my team registry or the descriptor?**
The **component descriptor** is the single source of truth for ownership. If a
team's `ownership/components.yaml` disagrees, validation fails and you fix the
descriptor, not the registry.

## Daily workflow

**How does a change move from idea to done?**
Discovery brief → PRD → implement → `prd complete`. Full path:
[how-to/take-a-change-from-discovery-to-done.md](../how-to/take-a-change-from-discovery-to-done.md).

**Why does `prd complete` refuse to finish?**
It enforces "done means reality actually changed." It blocks while any
governance checklist item is still `- [ ]`, or while a listed component's
reality doc has an `updated:` date older than the PRD's `created:` date. Check
the boxes for real, or update the reality doc (and its `updated:` date).

**How do I check my work before claiming it's ready or done?**
[how-to/check-your-work-against-governance.md](../how-to/check-your-work-against-governance.md)
covers `company-os check ready|done`.

**I edited a generated file and it keeps coming back — why?**
Derived content (tags, the `CLAUDE.md` context node, feature indexes) is
regenerated by `company-os graph build`. Don't hand-edit it; change the source
and rebuild. Validation flags the drift until you do.

## Validation

**What is `company-os validate` actually checking?**
The shared contract: frontmatter core, tag derivation, ownership
reconciliation, expiring deviations/exceptions, derived-content drift, skill
conflicts, and (if federated) governance-slice integrity. Each gate `[n/N]`
maps to one check — [how-to/run-the-validation-gate.md](../how-to/run-the-validation-gate.md).

**A gate failed and I don't understand the message.**
Look up the gate number in the Company OS table in
[reference/troubleshooting.md](troubleshooting.md) — it lists symptom → cause →
fix for each one.

**A command dies with a "team not found" error.**
Most `discover`/`prd`/`check`/`governance resolve` commands functionally need
`--team <id>` even though `--help` makes it look optional. Confirm the id with
`company-os ids list --prefix team://`.

**`company-os workspace ...` errors immediately.**
Those commands need a `workspace.yaml` manifest at the root. If you're a plain
monorepo with no federation, you don't need them — just use `validate`
directly.

## Search

**How do I make my workspace searchable from the terminal or an agent?**
Install Local Search, register the workspace, and wire up the Claude skill —
[tutorials/03-search-your-workspace.md](../tutorials/03-search-your-workspace.md).

**Search returns nothing / stale / weird results — what first?**
- Nothing expected: check `local-search repo list` + `local-search stats`,
  then `local-search scan`.
- Stale: `local-search scan` (or `scan <repo>`).
- Corrupt-looking: `rm ~/.local-search/specs.db` (safe, disposable cache).

Full table: [how-to/keep-search-fresh.md](../how-to/keep-search-fresh.md).

**A file I know exists is never found.**
Only `.md`, `.mdx`, and `.txt` are indexed directly. Give other files a `.md`
sidecar, or convert them. Change detection also needs the repo to have at
least one commit and `git` on `PATH`.
